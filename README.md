## 这是什么

你在 Obsidian 里存文章：知乎回答、公众号推文、技术博客、论文笔记、行业报告……越攒越多，但从来没有好好整理过。

你想让 AI 帮你整理——分类、打标签、建双链、编译概念页——但你怕它乱改你的笔记。删了正文、搞乱了 frontmatter、误改了只读文章……AI 不靠谱的时候，修都修不回来。

这个项目解决的就是这个：**用权限分区 + 脚本硬约束 + Git 版本控制，让 AI 能干活但不会闯祸。**

不只是"一套规则文件"，而是一整套可以交付的模板。你下载下来，改几个路径，对 Agent 说"入库"，它就开始整理你的收件箱。

## 为什么需要这个方案

### 问题一：AI 不可控

你告诉 AI"帮我整理笔记"，它可能：

- 把正在写的草稿改了
- 把精心维护的 Wiki 概念页覆盖了
- 删了你不想删的标签
- 在只读文章里乱写双链

**解决**：四区权限。AI 只能在活动区自由操作，需授权区脚本硬拦截，禁止区碰都不行。

### 问题二：改了回不去

AI 改完 20 篇文章，你发现其中 3 篇有问题——但你已经不知道哪些改了、怎么改回去。

**解决**：每次操作前 Git 快照，操作后提交。搞坏了随时 `rollback`。

### 问题三：不知道发生了什么

AI 默默干了一堆活，你不知道它做了什么、什么时候做的、有没有出错。

**解决**：管理日志 + 错误日志，每次操作强制执行，不写日志不算干完。

### 问题四：双链混乱

今天给 A 建了链接到 B，明天忘了，又建一遍。重复链接、漏掉链接、错链接——一团乱。

**解决**：三阶段入库。整理不管链，Wiki 不管链，最后统一提方案、你审一次、脚本一次建完。同一篇文章多次调用自动累积去重。

## 核心设计

### 设计理念

> **AI 做执行，人做判断。AI 不知道的，问你；AI 不会的，脚本兜底。**

不是"AI 全自动管理"，而是"人机协同"——AI 读文章、提建议、干体力活，你做所有关键决策。

### 四区权限

| 颜色 | 区域 | 权限 | AI 能干什么 |
|------|------|------|------------|
| 🔵 | `00-收件箱/` | 自由读写 | 创建、修改、删除、建链 |
| 🟡 | `01-素材库/` `03-思考/` `04-项目/` `05-产出/` | 脚本硬拦截 | 什么都不能干——除非你明确授权 |
| 🟢 | `02-Wiki/` | 只能追加 | 追加关联文章、_index.md 追加新条目 |
| 🔴 | `06-系统/` | 完全禁止 | 碰都不行——模板和规则是基石 |

**为什么不是"规则约束"而是"脚本硬拦截"？**

因为 AI 不读规则的时候你拦不住它。脚本直接拒绝写入，物理隔离。

### 三阶段入库

```
阶段一：整理分类 → 阶段二：编译 Wiki → 阶段三：统一建链 → 移动归档
```

每个阶段都有你的审核点。AI 不会自己闷头改。

### Git 版本控制

```
操作前 git snapshot → 操作 → 操作后 git commit → 写管理日志
```

出错了 `python scripts/git_control.py rollback` 回滚到上一个版本。

## 安装详解

### 第一步：下载项目

```bash
git clone https://github.com/hxlvcl/obsidian-agent-kb.git
cd obsidian-agent-kb
```

你会看到四个目录：`agent/`、`skills/`、`scripts/`、`vault/`。

### 第二步：替换占位符

项目里的文件用 `{{...}}` 作为占位符。你需要把它们换成你自己的路径。

**需要改的文件：**

| 文件 | 占位符 | 改成什么 | 示例 |
|------|--------|----------|------|
| `scripts/safe_link_appender.py` | `{{VAULT_PATH}}` | Obsidian Vault 绝对路径 | `D:\MyNotes` |
| `scripts/git_control.py` | `{{VAULT_PATH}}` | 同上 | 同上 |
| `scripts/audit_rules.py` | `{{VAULT_PATH}}` | 同上 | 同上 |
| `agent/AGENTS.md` | `{{VAULT_PATH}}` | 同上 | 同上 |
| `agent/AGENTS.md` | `{{WORKSPACE_PATH}}` | Agent 工作区路径 | `C:\Users\xxx\.agent\workspace` |
| `agent/MEMORY.md` | `{{VAULT_PATH}}` | 同上 | 同上 |
| `agent/MEMORY.md` | `{{GITHUB_REMOTE}}` | Vault 的 GitHub 远程地址 | `https://github.com/xxx/notes.git` |
| `agent/MEMORY.md` | `{{GITHUB_USER}}` | GitHub 用户名 | xxx |
| `agent/MEMORY.md` | `{{HOME_PATH}}` | 用户主目录 | `C:\Users\xxx` |
| `agent/BOOTSTRAP.md` | `{{VAULT_PATH}}` | 同上 | 同上 |
| `vault/知识库管理指南.md` | `{{VAULT_PATH}}` | 同上 | 同上 |
| `vault/知识库管理指南.md` | `{{GITHUB_REMOTE}}` | 同上 | 同上 |

**最简单的方法**：用编辑器的"全局搜索替换"，把所有 `{{VAULT_PATH}}` 替换为你的 Vault 路径。

### 第三步：部署到 Obsidian

把 `vault/` 里的**所有文件**复制到你的 Obsidian Vault 根目录。

注意：
- 不要把 `vault/` 文件夹本身复制进去——复制里面的内容
- 目录结构（`00-收件箱/`、`01-素材库/`、`02-Wiki/`……）会直接出现在你的 Vault 根目录
- 如果已有同名目录，不会覆盖你的文件，只是新增文件和子目录

### 第四步：初始化 Git

在 Vault 根目录执行：

```bash
cd "你的Vault路径"
git init
git add -A
git commit -m "init: 初始化知识库"
```

（如果你已经有 Git 可以跳过。但强烈建议用 Git——这是回滚的基础。）

### 第五步：部署 Agent

把 `agent/`、`skills/`、`scripts/` 三个目录放到你的 Agent 工作区。

不同的 Agent 平台路径不同，放到 `WORKSPACE_PATH` 对应的位置即可。

### 第六步：验证

对 Agent 说"入库"，它会：

1. 读取收件箱里的文章
2. 提出分类建议，等你确认
3. 清理文章 frontmatter
4. 暂留收件箱，等你确认 Wiki 方案
5. 提关联方案表格，等你审核
6. 脚本建链，移动到素材库

如果你在任何一步拒绝了，AI 不会继续。这就是"每一步你说了算"。

## 权限分区详解

### 为什么是四个区

这是从血泪教训中总结出来的。

**第一阶段：无分区。** AI 在知识库里随便改——改错了 20 篇文章，回滚都累死。

**第二阶段：规则约束。** 告诉 AI"不要改素材库""不要碰系统文件"。但 AI 有时不读规则，有时读错了规则，有时记错了规则。约束靠自觉，不可靠。

**第三阶段：权限分区 + 脚本硬拦截。** 不是"告诉 AI 别碰"——是"AI 想碰也碰不了"。

### 每个区的含义

#### 🔵 活动区：`00-收件箱/`

AI 可以自由创建、修改、删除文件。入库流程全程在此操作——清理 frontmatter、写占位符、建双链，都在收件箱完成。建链确认无误后才移走。

**为什么建链要在收件箱完成？** 因为如果建链时发现错了，直接在这改就行，不会影响素材库。

#### 🟡 需授权区：`01-素材库/` 等

已归档的文章都在这里。AI **没有权限碰**——`safe_link_appender.py` 会直接拒绝，打印 `[REJECT] BLOCKED`。

如果确实需要改（比如修正分类），你明确授权后，AI 才可以操作。

#### 🟢 半只读区：`02-Wiki/`

AI 可以追加，不能覆盖。具体来说：

- 可以在概念页末尾追加关联文章
- 可以在 `_index.md` 末尾追加新条目
- 不能删除已有内容
- 不能修改已有概念页的正文（只能追加）

#### 🔴 禁止区：`06-系统/`

模板和规则文件。AI 完全不可碰。这是知识库的基石，基石动了整个系统就崩了。

## 入库流程详解

完整的 19 步流程见 `vault/06-系统/入库流程完整版.md`。这里是关键要点。

### 阶段一：整理入库（步骤 0-8）

**你在这一步做什么**：确认分类。

AI 会：
1. 扫描收件箱，读每篇文章的正文
2. 提分类建议（文章 A → `01-素材库/教程/`，文章 B → `01-素材库/技术概念/`……）
3. **等你确认**后，清理 frontmatter、清理残留行、在正文末尾写占位符 `**关联文章**\n\n（待统一建链）`
4. 文件留在收件箱，Git 提交标注"待建链"

**文件为什么留在收件箱？** 因为下个阶段还要在上面建链。建完链才移走。

### 阶段二：编译 Wiki（步骤 9-13）

**你在这一步做什么**：审核 Wiki 变更方案。

AI 会：
1. 扫描 `02-Wiki/`，判断新文章匹配哪个概念页
2. 提 Wiki 变更方案表格：

| 文章 | 操作 | 目标 |
|------|------|------|
| 文章A | 增量更新 | `02-Wiki/01-科技/Skill生态.md` |
| 文章B | 新建概念页 | `02-Wiki/03-哲学/xxx.md` |
| 文章C | 仅索引 | `_index.md` 01-科技 |

3. **等你审核**确认后才执行
4. **不涉及任何链接操作**——Wiki 只管内容，不管链

### 阶段三：脚本建链 + 移动归档（步骤 14-19）

**你在这一步做什么**：审核关联方案。

AI 会：
1. 扫描全库，提关联方案表格，**每行一个关联关系**：

| 文章 | 关联文章 | 理由 |
|------|---------|------|
| A | B | 同主题 |
| A | C | 同作者 |
| B | D | 引用观点 |

2. **等你审核**确认后，逐行构造命令执行：

```bash
python scripts/safe_link_appender.py --new-article --target "00-收件箱/A.md" --links "B"
python scripts/safe_link_appender.py --new-article --target "00-收件箱/A.md" --links "C"
python scripts/safe_link_appender.py --new-article --target "00-收件箱/B.md" --links "D"
python scripts/safe_link_appender.py --wiki-concept --target "02-Wiki/01-科技/xx.md" --article "A"
python scripts/safe_link_appender.py --wiki-index --category "01-科技" --entry "[[A]] — 摘要"
```

3. 同一篇文章多次调用——脚本自动累积去重，不会覆盖
4. 建链完成后移动到素材库
5. Git 提交 + 管理日志

### 为什么表格每行只有一个关联目标

因为这样你审核时一目了然——每个关联关系都有独立的理由。如果一行"B, C, D"，你看不出为什么关联。

脚本支持多次调用同一篇文章自动累积去重，所以不需要合并。

## 脚本详解

### safe_link_appender.py

**作用**：安全地往知识库文件追加双链。不通过这个脚本，AI 没法碰需授权区。

**三种模式**：

| 模式 | 命令 | 用途 |
|------|------|------|
| `--new-article` | `--target "收件箱/文章.md" --links "目标"` | 在文章末尾的 `**关联文章**` 区块追加链接 |
| `--wiki-concept` | `--target "Wiki/概念页.md" --article "新文章"` | 在 Wiki 概念页追加文章来源 |
| `--wiki-index` | `--category "01-科技" --entry "[[文章]] — 摘要"` | 在 `_index.md` 追加索引条目 |

**安全机制**：

```
请求写入 → 检查是否在白名单 → 是 → 执行
                              → 否 → [REJECT] 打印原因并拒绝
```

白名单：`00-收件箱/`、`02-Wiki/`
黑名单：`01-素材库/`、`03-思考/`、`04-项目/`、`05-产出/`、`06-系统/`

**追加模式**：同一篇文章多次调用自动累积，不会覆盖已有链接。如果链接已存在，自动跳过。

### git_control.py

**作用**：操作前快照，操作后提交，出错了回滚。

```bash
# 操作前快照
python scripts/git_control.py pre "入库整理：3篇"

# 操作后提交
python scripts/git_control.py post "入库完成：3篇 → 分类完成"

# 回滚到上一版本
python scripts/git_control.py rollback

# 恢复单个文件
python scripts/git_control.py restore "00-收件箱/某文件.md"

# 查看最近提交
python scripts/git_control.py status
```

### audit_rules.py

**作用**：分析错误日志，聚类相似错误，给出规则改进建议。

当 AI 出错了、回滚失败了、脚本报异常了——这些都会自动记录到错误日志。`audit_rules.py` 会定时扫描错误日志，帮你：
1. 发现高频错误类型
2. 聚类分析根因
3. 提出规则改进建议

## 管理日志与错误日志

这两个文件是整个系统"可追溯"的基础。没有它们，出了事你不知道发生了什么。

### 管理日志

**位置**：`vault/04-项目/管理日志.md`

**什么时候写**：每次 Git 提交后立即写。不写日志不算干完活。

**写什么**：
- 入库了什么文章（文件名 + 分类）
- 改了哪些规则
- 修复了什么问题
- 配置有什么变更

**格式**：
```markdown
## 2026-04-29

### 入库记录
| 文章 | 分类 | 结果 |
|------|------|------|

### 修复记录
| 问题 | 原因 | 是否解决 |

### 配置更改
| 操作 | 结果 |
```

**为什么重要**：三天后你问 AI"上次入库了什么"，AI 翻管理日志比翻 git log 快得多。git log 只告诉你"提交了"，管理日志告诉你"做了什么、为什么"。

### 错误日志

**位置**：`vault/04-项目/错误日志.md`

**什么时候写**：
- 入库自检失败
- Git rollback 失败
- safe_link_appender 错误
- 任何意外异常

**写什么**：
- 发生时间
- 错误类型
- 具体错误信息
- 当时的操作上下文
- 是否已修复

**格式**：
```markdown
### 2026-04-29 19:30 — 入库自检失败

**错误**：frontmatter 缺少闭合 `---`
**文件**：`00-收件箱/某文章.md`
**原因**：清理残留时误删了第二个 `---`
**修复**：rollback → 重新清理 → 已修复
```

**为什么重要**：不记错误日志的系统修不了 bug。`audit_rules.py` 依赖错误日志做聚类分析。如果同样的错误反复出现，聚类分析会发现并建议修改规则。

## 常见问题

### Q: 我只想用其中一部分，可以吗？

可以。每个组件都是独立可用的：

- 只想用权限分区？部署 `vault/` + 改 Agent 规则
- 只想用入库脚本？部署 `scripts/` + `skills/`
- 只想用 Git 版本控制？部署 `scripts/git_control.py` 即可

但不建议阉割——整套配合效果最好。

### Q: 我能改目录结构吗？

可以。但改完后必须同步更新 `safe_link_appender.py` 里的 `ALLOWED` 和 `BLOCKED` 列表，以及 `知识库管理指南.md` 里的目录结构说明。

### Q: Agent 不听话怎么办？

先看错误日志。大概率是权限拦截了——`safe_link_appender.py` 会打印 `[REJECT]` 并说明原因。

如果是规则问题（AI 没读规则），确认 Agent 工作区的 `agent/` 文件正确部署。

### Q: 怎么回滚？

```bash
cd "你的Vault路径"

# 回滚整个 Vault 到上一版本
python scripts/git_control.py rollback

# 只恢复一个文件
python scripts/git_control.py restore "00-收件箱/某文件.md"
```

### Q: 为什么要有管理日志？Git log 不够吗？

Git log 只告诉你"什么时候提交了"，不告诉你"为什么"。

管理日志记录的是**人的决策**——为什么把文章分到某个类、为什么建这条双链、为什么改这个规则。这些信息 Git log 没有。

### Q: 这个方案适合多大的知识库？

没有上限。权限分区和脚本硬约束跟笔记数量无关——10 篇和 10000 篇，安全机制一样工作。

目录结构取决于你的需求。`01-素材库/` 下的子目录可以自己扩展。

## 踩坑经验

这套方案是在无数次犯错中迭代出来的。分享几个关键教训：

### 不要只用规则约束 AI，用脚本硬拦截

早期方案是"规则说 AI 不能碰素材库"——但 AI 有时不读规则、有时读错、有时忘记。换成 `safe_link_appender.py` 白名单硬拦截后，这个问题彻底解决了。

### 入库不要一步到位，分三阶段

早期方案是"入库=分类+建链一步完成"。结果是：分类意见和链接意见混在一起，审核混乱；Wiki 编译时不知道文章在哪；建链时发现分类不对要回头改。拆成三阶段后，每阶段只做一件事，思路清晰。

### 文件先留在收件箱，建完链再移走

早期方案是"清理完就移到素材库"。但后续建链要改文件内容，素材库是只读区，脚本拒绝写入。改成"暂留收件箱→建链→再移走"，物理上解决了这个问题。

### 表格每行一个关联目标，不要合并

早期表格是一行多个目标：`A | B, C | 同主题`。但每行只能有一个理由，多个目标混在一起你不知道为什么关联。改成每行一个目标后，审核清晰多了。

### 管理日志不能事后补

早期习惯"先干活，做完再一起写管理日志"。结果是经常忘记写、写漏条目、记错顺序。现在是"每次 Git 提交后立即写"，不再遗漏。
