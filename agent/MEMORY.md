## 用户偏好（从交互中积累）

### 工作方式偏好
- **一次性确认**：分类建议 + 链接建议合并提，用户一次确认，不等两次
- **先做计划再动手**：复杂任务先建 plan，用户确认后逐步执行
- **测试验证**：部署完成后模拟完整流程测试，展示结果
- **AI 自己完成技术实施**：用户期望 AI 独立完成技术工作，这是提升机会

### 管理日志偏好
- **需要顶层总结概述**：详细条目前加一段总结，一眼看到今天做了什么
- **结构性变更必须立即记录**，不做完再补（每次 Git commit 后紧接着更新管理日志）
- **排序规则**：独立条目按时间倒序（最新事排最前）；同任务链条目按执行顺序排列（1→2→3→4），归在同一日期下

### 流程设计偏好
- **精简化**：去掉冗余步骤（如 .bak 备份在 Git 存在时是浪费）
- **步骤编号需严谨**：增删步骤后全局重新编号
- **关联文件同步更新**：改动涉及多个文件时全部同步修改

### 格式一致性原则
- **任何新记录系统，优先复用知识库已有格式**（管理日志 = markdown 标头 + 字段值），不自行设计新格式
- 不确定格式时，先问用户再动手

### 不要这样做
- ❌ 替用户决定双链关系 — 同作者/同生态不等于该互链
- ❌ 凭记忆猜测配置字段名 — 写插件配置前先查源码或文档
- ❌ 不备份就修改 — 不可逆
- ❌ 不读就 write_file — 会覆盖正文
- ❌ 规则文件与 AI 身份定义混在一起 — 知识库管理指南只放管理规则，AI 身份归工作区文件

## 工作原则

### 核心准则
- **不删除，只整理**
- **不懂就问，不瞎猜**
- **主动建议，不等命令**
- **每次纠正都是成长机会**
- **用户的"不要这样"比"这样很好"更重要**
- **只改用户指出的问题** — 用户说修哪个就修哪个，不主动扫描/修改其他文件（即使有类似问题）；不确定是否要一起处理的，先问用户
- **规则不需要一上来完美，在错误中成长**

### 协调准则
- **知道自己什么时候够用，什么时候该找专家**
- **不代替专家回答专业问题**
- **收到专家回答后直接转述，不加工**

## 高价值经验

### 权限分区 > 规则约束
之前所有事故（误删正文、格式搞乱、YAML 失效）的核心原因是 AI 能在所有目录随意操作。分区后：
- 活动区（`00-收件箱/`）随便改，大不了回滚
- 只读区（`01-素材库/`等）只能建链，不能改内容
- 禁止区（`06-系统/`）压根不能碰

### 入库流程关键决策（用户确认）
- 自检对照：用 `06-系统/模板/新笔记.md` 对照，不用内联模板
- 步骤顺序：先读规则文件（知识库管理指南.md + AGENTS.md），再 Git snapshot
- 第5步合并：一次性提出分类 + 链接建议，用户一次确认
- 清除残留：正则匹配 `^作者[:：]` `^时间[:：]` `^来源[:：]` `^\d+ 人赞同`
- Git 提交格式：`"入库：完成 N 篇 → {文件名1, 文件名2}"`
- 自检失败：执行 rollback + 报告原因 + 终止流程
- 防范递归：同步规则文件时不得触发入库流程

### Phase 3 升级要点
- **流程从13步扩至14步**：新增"编译/更新Wiki概念页"（强制），嵌入在移动文件后、Git提交前
- **三份同步更新**：入库流程完整版.md + 知识库管理指南.md + SKILL.md（obsidian入库 v3.0）
- **Wiki编译四步判断**：扫描匹配→更新/新建/仅索引
- Wiki 为只读区，仅用户授权可修改

### Wiki 概念页设计原则
- 概念页是**多篇文章汇聚的枢纽**（Hub），而非单篇文章的标签
- 分类参照维基百科顶层分类，不照搬全部
- 每类下不设子目录，靠 `[[双向链接]]` + `_index.md` 建立层次
- 每次入库强制编译 Wiki（增量更新）

### 错误日志系统
- 位置：`04-项目/错误日志.md`
- 格式：markdown（`### 标题` + `**字段**：值`），与管理日志一致
- 写入时机：回滚失败时自动写入（入库流程第7步 + SKILL.md第6步）
- 配套工具：`scripts/audit_rules.py` — 解析错误日志 → 聚类分析 → 规则改进建议

### Git 版本控制注意事项
- Obsidian Git 插件自动备份字段名是 **`autoSaveInterval`**，不是 `autoCommitInterval` — 写错 key 配置不生效，插件用默认值 0。必须从插件源码或文档查清字段名再写配置
- 插件注册到 `community-plugins.json` 后，还需用户在 Obsidian 设置中手动启用
- 本地分支 `master` → `main`（GitHub 默认用 main）
- `git_control.py pre` 在脏工作区时会将变更纳入快照提交（label 显示 [pre]）；`post` 检测到无新变更时会跳过提交 — 此为正常行为

### 入库流程 v4.0：三阶段分离

| 阶段 | 操作 | 建链 |
|------|------|------|
| 一 | 入库（清理+分类），`related: []`，DataviewJS 空占位 | ❌ |
| 二 | 编译 Wiki（增量更新，匹配/新建/索引三分支） | ❌ |
| 三 | 统一建链：AI 提表格（文章→关联→理由），用户审一次，写入 `**关联文章**` + `[[双链]]` | ✅ |

Wiki 判断：匹配→增量追加 | 无匹配有价值→新建概念页 | 无匹配较浅→仅_index

### 关联文章格式（当前方案）

正文末尾直接写 `[[双链]]`，格式：

```
**关联文章**

[[文件名1]]
[[文件名2]]
```

- 不用 DataviewJS（已移除）
- 不用 `→ 相关：` 前缀
- 不用 `related:` frontmatter 字段
- 双链直接放正文，图谱能认

### 双链操作铁律（血的教训）

1. **`edit_file` 禁止用 `---` 当锚点** — 会匹配全文件所有分隔线，炸成几千行
2. **批量改完必须抽查 ≥3 个文件** — 第1个、中间1个、最后1个
3. **不写内联 Python** — cmd 里 `python -c` 缩进/编码/文件名全炸，写 `.py` 脚本
4. **出错先 git restore** — 不手工修，恢复→分析→修正脚本→重跑
5. **格式变更先单文件确认** — 用户说方向→改一个→确认→批量
6. **正则先测试后批量** — 在 1 个文件上看命中再跑全量

### 文件操作陷阱
- 重建 YAML 时用 `'---\n'` 开头，不要用 `parts[0] + '\n---\n' + parts[1]`（会导致空行使 YAML 失效）
- frontmatter 中的 `[[链接]]` 默认不在 Obsidian 图谱中显示，必须同步写到正文末尾
- 双链格式：`[[标题1]], [[标题2]]`，不需要外层 `[]`
- YAML 字段值必须全部用双引号包裹 `"..."`；摘要（summary/abstract）字段中禁止使用中文双引号 `""`，改用单引号 `''`，否则 frontmatter 报红
- 超长文件名可为笔记添加 `aliases` 字段，用短名称简化链接书写
- 不读文件直接 write_file = 覆盖正文（不可逆）
- 不备份就修改 = 无法恢复
- 用 `edit_file` 替换区块时，检查替换前后边界是否对齐，避免破坏相邻结构
- **`edit_file` 用 `---` 当锚点会匹配全文件所有分隔线** → 只能用唯一字符串
- 文件名含 `→`/`—` 会导致 Obsidian `[[链接]]` 解析截断 → 必须注册 `aliases` 短名
- HTML 注释 `<!-- -->` 在 Obsidian 实时预览模式下可见 → 不能用来藏内容
